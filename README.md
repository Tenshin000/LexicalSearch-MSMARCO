A Fast Traditional Information Retrieval Pipeline. Project for the exam of Multimedia Information Retrieval and Computer Vision at the University of Pisa for the Master's Degree in Artificial Intelligence and Data Engineering. 

The project is a high-performance lexical search engine, developed entirely in Python for Information Retrieval over the MS MARCO Passage collection (consisting of approximately 8.8 million documents), architected to operate under the strict RAM constraints of Google Colab. The data lifecycle begins with a heavily optimized, low-level text preprocessing stage: textual documents are normalized using the NFKD decomposition provided by the `unicodedata` library, combined with a C-level ASCII filter, allowing accents and special characters to be removed without resorting to slow replacement loops. Subsequently, valid token extraction (including abbreviations and textual numbers converted on the fly into digits through a static O(1) mapping) is performed in a single pass using precompiled regular expressions. Stopword filtering relies on a `frozenset` to guarantee constant-time lookup while avoiding reallocation overhead, whereas final stemming is delegated to the Cython backend of the `PyStemmer` library, which processes the entire document token list in a single C-level batch.

During Inverted Index construction, documents are iterated sequentially through a `defaultdict(list)` to optimize posting-list initialization, but the most crucial architectural aspect is ID remapping: the original textual dataset identifiers are replaced with a sequence of dense integers (from 0 to N). This transformation provides a dual advantage: on the one hand, it allows document lengths to be stored in contiguous memory for constant-time O(1) access during scoring; on the other hand, it mathematically minimizes the delta gaps (d-gaps) between documents within the same posting list. This numerical density is the fundamental prerequisite for the next architectural layer, namely compression through the C++ FastPFor (`simdfastpfor256`) library.

The system compresses document-ID arrays by applying d-gaps and the PForDelta algorithm, while using standard PFor for term frequencies (TF). It delegates to the processor, through SIMD vector instructions, the selection of the optimal number of bits to use and the extraction of outliers into separate patches. Everything is managed in memory through NumPy buffers and using a destructive approach (`.pop()`) that deletes the original index as it is progressively compressed, preventing Out-of-Memory errors.

For querying the index with on-the-fly decompression, the system provides a custom iterator equipped with NextGEQ (Next Greater or Equal) logic based on the `bisect` module, guaranteeing logarithmic-time jumps within posting lists. Relevance computation is based on two similarity functions: the classic BM25 (with optimized $k_1$ and $b$ parameters) and a rigorous TF-IDF implementation that uses sublinear logarithmic damping of term frequency to avoid excessively penalizing long documents.

These formulas are applied by two distinct implemented scorers: the Term-At-A-Time (TAAT), which fully evaluates one posting list at a time while accumulating partial scores in a `defaultdict`, and the Document-At-A-Time (DAAT), which synchronizes parallel advancement across all query iterators using a Min-Heap priority queue, scanning the corpus one document at a time. Both scorers share a critical optimization for handling duplicate query terms: textual queries are first condensed into a `Counter` of term frequencies, allowing the algorithm to decompress and iterate over a single posting list while simply multiplying the partial score by the term-occurrence factor, drastically reducing I/O time.

Top-K result filtering for each query is handled by a `TopQueue` structure (another Min-Heap), which keeps only the best K documents in memory while iteratively discarding lower scores at a cost of O(N log K), ultimately resolving the inverse mapping to return the original string IDs.

The entire engine is validated along two dimensions. In terms of effectiveness, it is evaluated on the TREC Deep Learning 2020 queries using the `ir_measures` framework, which sequentially computes deep-ranking and precision metrics (nDCG@10, MAP, MRR, Bpref). The intrinsic penalty associated with documents retrieved by the engine but not present in the annotated dataset (and therefore automatically assigned a relevance score of zero) is monitored and mitigated through the high Judged@10 score, ensuring a scientifically robust comparison even against enterprise-grade Java frameworks such as PyTerrier.

In terms of efficiency, TAAT and DAAT performance is compared using a Bootstrap execution model on randomized query samples to smooth out hardware-related anomalies. The resulting average latency and throughput (queries per second) are finally passed to a paired T-Test (Paired T-Test) based on the inverse of response time to normalize variance. This statistically demonstrates that, within the context of this Python search engine, the matrix-oriented structure of TAAT is clearly superior to DAAT in terms of execution speed.

This ultimately completes the design of a pure Information Retrieval system, free of Deep Learning, scalable, and pushed to the theoretical and practical limits of lexical and engineering optimizations.

Una pipeline rapida e tradizionale di Information Retrieval. Progetto per l'esame di Multimedia Information Retrieval and Computer Vision presso l'Università di Pisa, per il corso di laurea magistrale in Artificial Intelligence and Data Engineering. 

Il progetto è un motore di ricerca lessicale ad alte prestazioni, sviluppato interamente in Python per l'Information Retrieval sulla collezione MS MARCO Passage (composta da circa 8,8 milioni di documenti), architettato per operare sotto i rigidi vincoli di memoria RAM di Google Colab. Il ciclo di vita del dato inizia con una fase di preprocessing del testo pesantemente ottimizzata a basso livello: i documenti testuali vengono normalizzati tramite la scomposizione NFKD della libreria `unicodedata` accoppiata a un filtro ASCII in C, permettendo di rimuovere accenti e caratteri speciali senza ricorrere a lenti cicli di sostituzione. Successivamente, l'estrazione dei token validi (incluse sigle e numeri testuali convertiti al volo in cifre tramite una mappa statica O(1)) avviene in un unico passaggio tramite espressioni regolari precompilate. Il filtraggio delle stopword utilizza un `frozenset` per garantire un tempo di lookup garantito e privo di overhead di riallocazione, mentre lo stemming finale è delegato al backend Cython della libreria `PyStemmer`, che elabora l'intera lista di token del documento in un unico batch C-level.

Durante la costruzione dell'Inverted Index, i documenti vengono iterati sequenzialmente tramite un oggetto `defaultdict(list)` per ottimizzare l'inizializzazione delle posting list, ma l'aspetto architetturale più cruciale è la rimappatura degli ID: gli identificativi testuali originali del dataset vengono sostituiti da una sequenza di interi densi (da 0 a N). Questa trasformazione garantisce un duplice vantaggio: da un lato permette di mantenere le lunghezze dei documenti in memoria continua per un accesso in tempo costante O(1) in fase di scoring, dall'altro minimizza matematicamente i delta-gaps (d-gaps) tra i documenti nella stessa posting list. Questa densità numerica è il prerequisito fondamentale per il livello successivo dell'architettura, ovvero la compressione tramite la libreria C++ FastPFor (`simdfastpfor256`).

Il sistema comprime gli array dei docID applicando i d-gaps e l'algoritmo PForDelta, mentre sfrutta il PFor standard per le frequenze dei termini (TF), delegando al processore (tramite istruzioni vettoriali SIMD) la scelta del numero ottimo di bit da utilizzare e l'estrazione degli outlier in patch separate; il tutto gestito in memoria tramite buffer NumPy e con un approccio distruttivo (`.pop()`) che cancella l'indice originale man mano che viene compresso, prevenendo errori di Out-Of-Memory.

Per l'interrogazione dell'indice decompresso al volo, il sistema fornisce un iteratore custom dotato di una logica NextGEQ (Next Greater or Equal) basata sul modulo `bisect`, garantendo salti in tempo logaritmico all'interno delle posting list. Il calcolo della rilevanza si basa su due funzioni di similarità: il classico BM25 (ottimizzato nei parametri $k_1$ e $b$) e un TF-IDF rigoroso che sfrutta uno smorzamento logaritmico sublineare sulla frequenza del termine, per evitare di penalizzare eccessivamente i documenti lunghi.

Queste formule vengono applicate da due distinti scorer implementati: il Term-At-A-Time (TAAT), che valuta interamente una posting list per volta accumulando i punteggi parziali in un `defaultdict`, e il Document-At-A-Time (DAAT), che sincronizza l'avanzamento parallelo in tutti gli iteratori di query avvalendosi di una coda di priorità Min-Heap, scorrendo il corpus un documento alla volta. Entrambi gli scorer condividono un'ottimizzazione critica per la gestione dei termini di query duplicati: le query testuali vengono prima condensate in un `Counter` delle frequenze, permettendo all'algoritmo di decomprimere e iterare una singola posting list moltiplicando semplicemente il punteggio parziale per il fattore di presenza del termine, abbattendo drasticamente i tempi di I/O.

Il filtraggio dei risultati top-K per ogni query è gestito da una struttura `TopQueue` (un'ulteriore Min-Heap) che mantiene in memoria solo i migliori K documenti scartando iterativamente i punteggi inferiori con costo O(N log K), risolvendo infine il mapping inverso per restituire gli ID stringa originali.

L'intero motore è validato su due fronti. Dal lato dell'efficacia (Effectiveness), viene valutato sulle query del TREC Deep Learning 2020 tramite il framework `ir_measures` che calcola in sequenza metriche profonde e di precisione (nDCG@10, MAP, MRR, Bpref); la penalità intrinseca per i documenti trovati dal motore ma non presenti nel dataset annotato (giudicati automaticamente a rilevanza zero) è monitorata ed elusa grazie all'elevato punteggio della metrica Judged@10, garantendo un confronto scientificamente robusto persino contro framework Enterprise in Java come PyTerrier.

Dal lato dell'efficienza, le performance di TAAT e DAAT vengono confrontate usando un modello di esecuzione Bootstrap su campioni di query randomizzati per smorzare le anomalie hardware; i risultati di latenza media e throughput (query al secondo) sono infine passati a un T-Test accoppiato (Paired T-Test) basato sull'inverso del tempo di risposta per normalizzare la varianza, dimostrando statisticamente che, nel contesto di questo motore Python, la struttura matriciale del TAAT risulta nettamente superiore in termini di velocità rispetto al DAAT.

E così si chiude il cerchio di un sistema di Information Retrieval puro, privo di Deep Learning, scalabile e spinto al limite teorico e pratico delle ottimizzazioni lessicali e ingegneristiche.
